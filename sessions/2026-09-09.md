## Notes
- **The original bug report (iPad nav rendering as a mix of the phone top-strip and the full
  desktop sidebar simultaneously) traced to a genuine CSS-cascade dead end, not a logic bug.**
  Read every rule touching `.sidebar`/`#mobile-nav`/`.eqf-side` across `base.css`, `mobile.css`,
  `field-v8.css` — the shell-mode nav-restore block that shows the top strip
  (`mobile.css` ~L955) and the block that hides the sidebar live inside the *identical* compound
  `@media` condition, so per the code as written the two literally cannot diverge. Diffed local
  HEAD against `origin/main` to rule out stale-checkout as the explanation (byte-identical on
  the relevant lines) before concluding it had to be something a plain reload doesn't reach.
- **Root cause: `sw.js`'s `CACHE_FIRST_PATHS` serves `/styles/*` straight from Cache Storage** —
  a reload re-asks the same stale-controlling service worker rather than fetching fresh CSS from
  the network. iOS Safari is known to lag on swapping in a new SW in the background (worse if
  the app is added to the Home Screen). No code fix — the unstick is clearing Safari's site data
  for the domain, which Royce hadn't done. This means the fix in PR #942 is unverified on his
  device until that happens even after he re-visits the site.
- **A PostHog device-mix check (SKS project `eq-production`, id 162632, 90 days, 969 unique
  visitors) grounded the "should we build this at all" question in real numbers rather than
  intuition.** `$device_type`/`$os` don't distinguish iPad from a real Mac at all — iPadOS's
  default "Request Desktop Website" mode makes Safari report as plain `Mac OS X`, confirmed via
  `read-data-schema` showing no Tablet/iPadOS value ever appears. Proxied via `$screen_width`
  instead: of the `Mac OS X`-reporting population, only ~6 people have a screen width ≤1024px
  (the only pattern that's unambiguously an iPad, not a real Mac) — generously counting the
  *entire* Mac-OS-X bucket caps it at 53. Either way, under 1–5% of traffic — small enough that
  it could be Royce plus one or two others, not a broad supervisor pattern. This is why the fix
  reuses existing components cheaply rather than investing in a bespoke tablet design.
- Isolated eq-field work into its own worktree (`eq-field-ipad-breakpoint-wt`,
  `claude/ipad-tablet-breakpoint`) per that repo's own shared-root convention; removed after
  merge. Ran into eq-context's own `/brief` session-gate hook mid-task (skipped it because the
  session had started as a debugging conversation, not a fresh task) — ran `/brief eq-field`
  properly before the blocked edits, Royce confirmed the brief, then the same edits went through.
- A real tool-capability gap surfaced at the very end of the session: there is no way in this
