## Notes
- **Real gotcha, hit twice this session, worth knowing for any future `@eq-solutions/*` version bump on a `github:`-pinned dependency:** `npm install` silently no-ops on re-resolving a git dependency when package.json and package-lock.json's *top-level* manifest declarations already agree — even if the deeper resolved commit in the lockfile is stale. It reports "up to date" and does nothing. The fix is an explicit `npm install <pkg>@github:owner/repo#tag` to force the real fetch. Always verify by reading `node_modules/<pkg>/package.json`'s own version after any lockfile-only bump — don't trust the npm install summary line.
- Reconfirmed (not new, but worth restating): this session's Claude Code auto-mode classifier blocks `merge_pull_request` outright, for any repo — not a per-repo or per-request thing, and not something a `gh` CLI substitution should be used to route around. Royce merged all three PRs himself from his phone.
- eq-shell's `package.json` description string and `eq-solves-service`'s local folder name both still don't match their actual GitHub repo names in places (`eq-service`, not `eq-solves-service`) — already a documented naming trap in CLAUDE.md, reconfirmed live via `gh` during this session, no action needed.
