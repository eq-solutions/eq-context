# Session 2026-08-05-y — My Schedule maps link fixed (iOS home-screen installs)

## Built
- Royce reported the maps link on the My Schedule page "wasn't working" on mobile. Grepped the whole eq-field repo and confirmed the "Open in Google Maps" icon in `scripts/roster.js` (`renderSchedule()`) is the only `maps.google.com` link in the app — one call site, not a broader pattern.
- Built a mocked-`STATE` harness that loads the real `app-state.js`/`utils.js`/`roster.js` and calls the actual shipped `renderSchedule()`, confirming the URL/encoding is correct against live SKS site-address data pulled directly from `app_data.field_sites` on ehow — ruled out a malformed-address theory before looking elsewhere.
- Root-caused via precedent already in this codebase: `site-reports-shared.js`'s v3.5.264 fix documents the identical failure class — `<a download>` blob links silently no-op in an iOS standalone PWA (Field added to the home screen) because there's no "new tab" for the browser to open. The maps icon used `target="_blank"`, same gap.
- Fix reuses that fix's existing iOS-standalone detection (`navigator.standalone` / `matchMedia('(display-mode: standalone)')`) rather than inventing a second implementation — drops `target="_blank"` only when standalone, so the tap becomes a same-window navigation that iOS intercepts as a Universal Link and hands off to the Maps app. Every other target (Android, desktop, iOS Safari tab) is unchanged.
- Verified the fix branches correctly by simulating iOS-standalone in the same harness (overriding `navigator.userAgent`/`navigator.standalone`) and confirming the anchor's `target` attribute is dropped only in that case.
- eq-field [PR #655](https://github.com/eq-solutions/eq-field/pull/655) (v3.5.459 → renumbered to v3.5.460 on merge), CI + deploy preview green, Royce said "merge" — squash-merged, branch deleted, production confirmed serving v3.5.460 via `sw.js`.
