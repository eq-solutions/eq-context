# Session 2026-08-06 (continued again) — EQ-SHELL-1D: proxy crashed on every write, found + fixed same day, zero data lost

*Royce: "Simon can view the quotes but they aren't saving (for him but check overall)." Turned out to be a real production incident in code shipped earlier this same session, not a Simon-specific problem.*

## Built
- Investigated via Sentry, not assumption: found [EQ-SHELL-1E](https://eq-solutions.sentry.io/issues/EQ-SHELL-1E)/[EQ-SHELL-1F](https://eq-solutions.sentry.io/issues/EQ-SHELL-1F) (browser-side "unknown error" on `eq_update_quote_status`/`eq_replace_line_items`) and traced them to a genuine server-side crash, [EQ-SHELL-1D](https://eq-solutions.sentry.io/issues/EQ-SHELL-1D): `TypeError: Response constructor: Invalid response status code 204` inside `tenant-data-proxy.ts` itself — 8 occurrences, first at 04:30:24 UTC, ~1 hour after PR #1263 (the proxy) went live.
- Root cause: `new Response(body, {status: upstream.status})` throws when status is 204/205/304 (the Fetch spec's null-body statuses) and body isn't literally `null`. PostgREST answers most writes/RPCs with 204 by default (`Prefer: return=minimal`, no returned row) — reads never hit this since PostgREST always sends a body on 200/206, which is exactly why it stayed hidden through the whole QuotesNative/LabourHireRates/Suppliers/Intake migration (all read-path traffic) until the first real save.
- **Before proposing or shipping any fix, verified whether data was actually lost** rather than assuming "not saving" meant "not saved": queried `app_data.quote_audit` and `app_data.quote_status_history` directly on ehow and matched all 8 crash timestamps 1:1 against real committed writes (5 line-item replaces, 3 status changes — Simon's 3 retries on the status change all landed the same "cancelled" state harmlessly). The crash happens after the upstream `fetch()` to PostgREST already succeeded, purely while formatting the response back to the browser — so nothing was ever at risk.
- Fix: pass `null` instead of `body` for the three null-body statuses (`NULL_BODY_STATUSES`, exported alongside the existing allow-lists for consistency). Added a regression test that constructs a real `Response` the same way the handler does, so a future regression fails in CI instead of only in production.
- Re-ran `/brief eq-shell` again (gate had re-armed after the last `/close`) rather than skip it, even under time pressure — git state was still clean/up to date from earlier the same session, so it was fast.
