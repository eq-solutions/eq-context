# Session 2026-08-19 — Cards iframe Web Share fix (eq-shell) + Wallet banner repeat fix (eq-cards)

## Built
- eq-shell [PR #1452](https://github.com/eq-solutions/eq-shell/pull/1452): `CardsIframe.tsx`'s `allow=""` → `allow="web-share"`, scoped narrowly (sandbox already restricts the rest). Unblocks the iOS Safari Web Share save path (eq-cards PR #274) when Cards is opened through the Shell embed instead of standalone. Merged, production deploy confirmed live via commit-ancestry check against the Netlify deploy record.
- eq-cards [PR #276](https://github.com/eq-solutions/eq-cards/pull/276): fixed the "You're ready for site" Wallet success banner reappearing on every visit through the Shell embed. Root cause (found by a bug-fixer subagent, verified against the vendored Supabase client source): the once-ever flag is namespaced by auth user id, but `Supabase.initialize()` doesn't await session restore, so a cold Flutter boot (every Shell iframe reload) could run the check before `currentUser` resolved, silently writing under the wrong key. Fix: skip the check entirely until the uid resolves, retry next rebuild. Merged, deploy workflow (`gh workflow run deploy.yml --ref main`) ran green, live on cards.eq.solutions.

- Royce approved running the eq-cards deploy workflow explicitly after the merge (deploy is gated behind `workflow_dispatch`, not automatic on merge).

## Deferred

- Couldn't rule out browser-level storage partitioning (Safari ITP / Chrome CHIPS) as a second contributing factor to the Wallet banner bug — inherent browser behaviour, not fixable in eq-cards; no Sentry/Chrome MCP access in that investigation session to check live frequency.

## Notes
- Follow-on sweep from the `staff_conversations` fix (eq-shell PR #1450, migrations 0250/0251): checked 6 more ehow tables that looked personal/performance-shaped by name (`feedback_entries`, `quarterly_reviews`, `skills_ratings`, `buddy_checkins`, `checkins`, `engagement_logs`) for the same RLS-tenant-wide-but-UI-implies-restricted pattern. None of the 6 currently hold data (0 rows each), and none are read/written from eq-shell (only referenced as static intake-pipeline routing labels in `netlify/functions/_shared/intake-modules.ts`).
- **Substrate correction — table-name collision on ehow.** `feedback_entries`, `quarterly_reviews`, and `skills_ratings` exist **twice** on ehow under different schemas with different column shapes and no relation to each other: `app_data.*` (apprentice_profile_id-keyed, intake-import twins, dead — nothing writes to them) and `public.*` (org_id/apprentice_id-keyed, the tables eq-field's own apprentices module — `scripts/apprentices.js`, `apprentices-feedback-forms.js`, `apprentices-reviews-rotations.js` — actually reads/writes for the SKS "in-place" tenant). Anyone grepping by table name alone will find the wrong one; check `information_schema.columns` with schema qualified before trusting a match.
- eq-field's apprentices module (the live `public.*` path) has **no permission gate anywhere** in the UI — no role check, no supervisor/manager restriction — on feedback, quarterly reviews, or skill ratings. Tenant-wide RLS is therefore consistent with the UI's own (unrestricted) design; this is the "expected visibility" case, not a gap, and needs no fix.
- Found but did not act on a second, unrelated oddity in the same tables: `public.feedback_entries/quarterly_reviews/skills_ratings`'s SELECT RLS policy checks a **hardcoded org_id literal** (`org_id = '00000000-0000-0000-0000-000000000002'`) instead of the requester's JWT tenant claim, while the paired write policy correctly checks both. In isolation that would be a cross-tenant read gap, but `authenticated`/`anon` have **zero table grants** on all three (verified via `has_table_privilege`), so the policy is currently unreachable from any client — reads harder as a stalled/broken feature (consistent with 0 rows in both table sets) than a live exposure. Left as-is; worth a look only if that feature is ever revived.
