## Notes
- **This directly corrects the "could not reproduce" note further up in this same file** (a concurrent session that checked `has_table_privilege('anon', 'public.app_config', 'SELECT')` and got `false`). That check ran AFTER this session's fix had already landed, not before — `has_table_privilege` checks whole-table privilege and doesn't detect a residual column-level grant, so it reads `false` both when a table was never anon-readable and when, as here, it was and got narrowed to specific columns. The original relayed claim was correct; the correction-of-the-correction is now in `eq/pending/eq-field.md`. Worth generalizing: a negative result from a privilege-check function needs the same "verify against the actual mechanism, not a proxy for it" scrutiny as any other live-state claim — `has_table_privilege` without a column list is the proxy here, `information_schema.column_privileges` (or a live HTTP smoke test with the real key) is the actual mechanism.

Worth keeping this order for any similar finding: catalog/grant inspection establishes the fact, a live request with the real key proves it end-to-end.
- Hit a real Postgres gotcha applying the fix: a column-level `REVOKE SELECT (value) ... FROM anon` is a silent no-op when the existing privilege came from a table-level `GRANT SELECT ON ... TO anon` — re-queried `information_schema.column_privileges` after the first attempt and found `value` still there. Fixed by revoking the table-level grant entirely, then re-granting back only the safe columns. Worth remembering for any future column-scoping fix on a table that currently has a blanket role grant.
