# Session 2026-08-05 — EQ-SHELL-10/19 root-caused and fixed: briefing engine trusted Claude's tool output shape with no validation

## Built
- **eq-shell — root-caused Sentry EQ-SHELL-10 ("auth-stall: chunk-error", 27 events) and EQ-SHELL-19 ("TypeError: l.brief.map is not a function", 8 events) as one incident, not two.** `generateBrief()` in `netlify/functions/_shared/briefing-engine.ts` cast Claude's `submit_briefing` tool-call output straight through with `as {...}` — no runtime check that `brief`/`actions`/`on_shift`/`upcoming` actually matched the declared schema. `tool_choice: { type: 'tool' }` forces Claude to call the tool but doesn't guarantee the arguments conform to `input_schema`; in production `brief` arrived as a plain string. `TenantHome.tsx`'s render guard (`aiData?.brief && aiData.brief.length > 0`) passes for any truthy value with a numeric `.length`, not just arrays, so the string reached `.map()` and crashed the `/sks` dashboard. `ChunkErrorBoundary` caught the throw, classified it `stuck-crash`, and reported it two ways (`captureMessage` → EQ-SHELL-10, `captureException` → EQ-SHELL-19) — confirmed same root cause from the captured event's extra data, which the task prompt already carried from an earlier `get_sentry_resource` call.
- Found the same unvalidated-shape gap also reaches `scheduled-briefing.ts` (the 9am daily briefing email cron), which reads the identical `generateBrief()` output with equally unguarded `.map()`/`.length` calls — so the same deviation could have been silently dropping a tenant's morning email with zero visible symptom, not just crashing the dashboard.
- Fixed at the single shared source: new `asStringArrayOrNull`/`asArray<T>` helpers in `briefing-engine.ts` coerce a wrong-shaped field to a safe default and report to Sentry if Claude's output ever deviates from schema again, rather than trusting it blindly. `TenantHome.tsx`'s render guard also got an explicit `Array.isArray` check, closing a narrow window where a bad shape already sitting in the 10-minute `briefing_cache` could survive one more read post-deploy.
