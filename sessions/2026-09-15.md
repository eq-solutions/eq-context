## Notes

**Root cause, converging from two independent angles:**

1. **Code reading (this session).** `handle_phone_dedup()` — the `auth.users` trigger that populates `shell_control.identity_recycle_review` — has exactly three lookup paths, and all three match a new phone-OTP signup against a phone number that must *already be on record* on some other identity (either `auth.users.phone` or `shell_control.users.phone`). There is no other signal — no name match, no email-domain match, no "same admin invited both" linkage. Separately, `netlify/functions/invite-user.ts` (the admin-invite endpoint) captures phone as an **optional** field: "Optional mobile — captured at invite time so the recipient can use the Mobile (phone-OTP) sign-in door from day one." When an inviting admin leaves it blank, nothing is ever on file for `handle_phone_dedup` to match against later.
2. **An existing, unconnected finding from the day before.** A Claude Code memory note from an eq-field session on 2026-09-14 (`project_madagins_onboarding_integrity_gaps`, item 5) already states as verified fact that Aditi (and Michelle) were provisioned via direct admin-invite, and that's *why neither had a phone anywhere in canonical at first — the admin-invite path doesn't ask for one*. Item 6 in that same note asks why the auto-detector missed the collision, without the session that wrote it noticing item 5 already answered item 6.

**Conclusion: `handle_phone_dedup()` almost certainly ran and correctly found no match.** This is not a scheduled job that failed to fire (it isn't one — it's a synchronous DB trigger, no cron involved) and not a bug in its matching logic. It's a phone-keyed detector with nothing to key against, for a person whose admin invite never captured a phone. No code change to `handle_phone_dedup` itself is indicated or would be correct.

Not verified against the live row — this session has no Supabase MCP access. If anyone wants certainty rather than strong inference, the one-query check is whether `02f5784c-0fe9-4289-aff4-150394bd4d6c` (Aditi's original identity) had a non-null `shell_control.users.phone` or `auth.users.phone` before 2026-09-13. That query would also confirm or rule out two secondary possibilities that don't need a design decision either way: `scu.active = false` on the original row at signup time, or a `normalise_au_phone()` edge case on either number's format.

**The actual lever, already named in the existing memory note, restated here since it's the real decision**: should `invite-user.ts` require or more strongly nudge admins to capture a phone at invite time? That's the only change that would let this specific detector catch this exact class of case going forward.

**Also found, ruled out, not chased further**: `eq-shell-wt-staff-phone-backfill` (uncommitted worktree, branch `claude/staff-phone-backfill`) looked relevant by name but isn't — different phone-data-quality problem (`cards-approve-staff.ts`/staff-licence-backfill functions), unrelated to identity dedup. Not touched.
