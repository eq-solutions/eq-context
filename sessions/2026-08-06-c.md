# Session 2026-08-06-c — My Schedule maps link, part two: tap-vs-long-press on iOS standalone

## Built
- Continuation of the 2026-08-05 maps-link fix (v3.5.460, PR #655). Royce click-tested it live and reported back: "it works but you need to hold down rather than tap the arrow button" — the hard no-op was gone, but a plain tap still didn't open Maps, only a long-press-then-Open from iOS's native link menu did.
- Root-caused as a second, more specific layer of the same iOS standalone problem: WebKit only hands a plain `https://` link off to another app via Universal Links (the `maps.google.com` -> Google Maps jump) on a "sufficiently deliberate" gesture. A long-press qualifies; a single tap in a home-screen-installed app doesn't — it just loads Google's page inside Field's own app shell instead of jumping to the Maps app.
- Presented the diagnosis and the fix trade-off to Royce before writing code: switch to Apple Maps' own `maps://` address for the iOS-standalone case only, since custom URL schemes aren't subject to the same tap-vs-long-press gate and open on a single tap. Apple Maps ships on every iPhone (can't be uninstalled), so there's no "app not installed" fallback needed. The real trade-off: installed-to-home-screen iPhone users now get Apple Maps for this link, everyone else (Android, desktop, plain Safari tab) still gets Google Maps. Royce: "ship the maps:// swap."
- Verified against the real shipped code via the same mocked-`STATE` harness pattern as the previous session: loaded the actual `app-state.js`/`utils.js`/`roster.js`, confirmed all three branches render correctly (default/Android/desktop and iOS-Safari-tab keep `https://maps.google.com/...` + `target="_blank"`; iOS standalone renders `maps://?q=...` with no target).
- eq-field [PR #659](https://github.com/eq-solutions/eq-field/pull/659) (v3.5.465), CI + deploy preview green (including the new bundle-drift gate from #658, unrelated), Royce said "merge" — squash-merged cleanly (fast-forward this time, no local branch-delete conflict like last session), production confirmed serving v3.5.465 via `sw.js`.
