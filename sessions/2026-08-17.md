## Notes
- **Recipient SET vs display-name upgrade is a real architectural distinction, not just caution.** For simple display pages, swapping wholesale onto the canonical roster is safe. For notification fan-out code, the actual recipient list must stay local-role-driven — RLS keys off the local `auth.uid()`, and Plan-B (Shell-embedded) sessions have no real Supabase Auth session at all, so a canonical-id-keyed recipient set would silently break delivery. Only the display name/email is safe to upgrade, via an email-keyed match. Worth remembering as the general pattern any time "swap X off tenant_members" comes up for fan-out/cron code specifically, not just single-user display code.
