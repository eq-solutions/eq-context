## Notes

- **Why `identity_collision_flags` doesn't apply, and what does instead.** That table's `new_user_id` column is `NOT NULL REFERENCES auth.users(id)` — it exists to record a new auth identity's phone/email matching an already-claimed worker. `eq_cards_admin_upsert_worker` never binds a `user_id` at all, by original design (0089: "linking a login is the job of the self-signup resolvers, not an admin edit") — there's no `new_user_id` to log, ever, for this function. A genuinely different, related gap was found instead: the same function's phone/email adopt-match can silently `UPDATE` an already-claimed worker (someone else's login) with no flag. Closed via a non-blocking `eq_write_audit_log` call, scoped by the pre-existing (0122) `is_worker_in_org` org check — which structurally means it can't fire across a tenant boundary.
- **Cross-session interruption, verified rather than accepted.** Mid-task, a peer session's cross-session message claimed eq-context decision 8 (`9fcbbaf1`, `eq/identity/AMBIGUITY-REGISTER.md`, settled by Royce same day) overturned this task's premise: two claimed workers sharing a phone — an SKS "work" identity plus a `__personal__`-tenant "wallet" identity — is decided as an intentional, common pattern (35 of 81 claimed workers), not a collision to flag or merge. Read the primary source directly rather than trusting the paraphrase: decision 8 answers a different, non-conflicting question (why two rows exist for one human — fine, don't touch it) from this session's task (why one row's name was blank — a data-quality gap in one specific RPC). The register's own live-verified table actually corroborates this session's finding — it independently describes `406d2b0f` as "no name, no email, phone-signup shape" and traces it as a pre-existing stub later claimed by a legitimate phone-OTP signup, which fits exactly: created blank-named by the admin-upsert bug, later claimed via a path that only ever sets `user_id` and never touches name fields.
