## Notes
- **Root cause.** `eq_cards_admin_upsert_worker`'s INSERT branch has never defaulted `first_name`/`last_name`, across any of its 5 tracked revisions (0011→0089→0112→0122→0131→0172, each read directly) — unlike every other worker-creation path in the suite (the two self-service resolvers default to `'Unknown'`; the `labour-hire-candidate-intake` edge function 422s on a fully-blank name). eq-cards' own Flutter admin form (`AdminWorkerFormScreen`) requires non-empty names client-side before it will even build the RPC payload, so jvkn `public.workers` row `406d2b0f-bf93-4959-b658-d65c3ac390d9` (created 2026-08-20, phone set, both names blank) was created by a direct RPC call bypassing that client-side check — the function's only server-side gate, `is_org_admin(p_org_id)`, enforces nothing about payload shape.
- **Why `identity_collision_flags` doesn't apply, and what does instead.** That table's `new_user_id` column is `NOT NULL REFERENCES auth.users(id)` — it exists to record a new auth identity's phone/email matching an already-claimed worker. `eq_cards_admin_upsert_worker` never binds a `user_id` at all, by original design (0089: "linking a login is the job of the self-signup resolvers, not an admin edit") — there's no `new_user_id` to log, ever, for this function. A genuinely different, related gap was found instead: the same function's phone/email adopt-match can silently `UPDATE` an already-claimed worker (someone else's login) with no flag. Closed via a non-blocking `eq_write_audit_log` call, scoped by the pre-existing (0122) `is_worker_in_org` org check — which structurally means it can't fire across a tenant boundary.
- **Cross-session interruption, verified rather than accepted.** Mid-task, a peer session's cross-session message claimed eq-context decision 8 (`9fcbbaf1`, `eq/identity/AMBIGUITY-REGISTER.md`, settled by Royce same day) overturned this task's premise: two claimed workers sharing a phone — an SKS "work" identity plus a `__personal__`-tenant "wallet" identity — is decided as an intentional, common pattern (35 of 81 claimed workers), not a collision to flag or merge. Read the primary source directly rather than trusting the paraphrase: decision 8 answers a different, non-conflicting question (why two rows exist for one human — fine, don't touch it) from this session's task (why one row's name was blank — a data-quality gap in one specific RPC). The register's own live-verified table actually corroborates this session's finding — it independently describes `406d2b0f` as "no name, no email, phone-signup shape" and traces it as a pre-existing stub later claimed by a legitimate phone-OTP signup, which fits exactly: created blank-named by the admin-upsert bug, later claimed via a path that only ever sets `user_id` and never touches name fields. No code change resulted from the cross-check; posted the full comparison as a PR comment so Royce wouldn't have to re-derive it at review time. Saved as a general working-pattern lesson in personal memory: a peer's "your premise is overturned" claim needs the cited primary source read directly — check it addresses the same *mechanism*, not just the same row/entity.
