- **Identity-fragmentation root cause found and fixed — the session's biggest finding.** While investigating why a fresh self-joined test account had no credential-gap alerts and an empty profile, traced it live: deleting a test account from `auth.users` (which is all I'd been doing on request, repeatedly, through this whole session) without also deleting Shell's own `shell_control.users` row leaves an orphaned row behind. `custom_access_token_hook`'s phone-fallback (added 2026-08-02, migration 0035, for a real and different bug — phone-format drift between two rows of the *same* person) has no way to distinguish that from "the real account behind this row was deleted" — it matched the orphan by phone and handed a completely different, later signup the deleted account's tenant/role, while that signup's own Cards-side rows (profile, org_membership) never got created because `shell-join-tenant.ts` had the identical gap on its own existing-user phone-match path and returned early.
  - This is a **real production gap**, not a test-only artifact — any legitimate account deletion/offboarding that skips the `shell_control.users` cleanup would trigger the same bug for a real worker.
  - Fixed both layers: `custom_access_token_hook` (eq-cards migration `0117` + PR #208 — one extra precondition: the phone-matched row must itself still have a live `auth.users` row) and `shell-join-tenant.ts`'s existing-user lookup (eq-shell PR #1229 — same guard via `sb.auth.admin.getUserById`).
  - Applied the DB hook change live to eq-canonical (jvkn) directly — auth-critical, Royce gave explicit go via an `AskUserQuestion` scoping check ("fix the blind spot now" → "also fix the systemic gap now"). Verified live, in a rolled-back transaction, both before and after applying: a real manager's claims (`eq_role`, `tenant_id`, `is_platform_admin`) are unaffected by the change.

## Notes
- **The identity-fragmentation bug was self-inflicted this session** (repeated test-account deletion via `auth.users` DELETE only, never touching `shell_control.users`) but the underlying gap it exposed is general and real — this is the kind of thing worth remembering when deleting *any* account, test or real, on jvkn: `auth.users`, `shell_control.users`, and `shell_control.user_tenant_memberships` all need to go together, or a later phone-reuse will silently misattribute identity.
- `worker_invites`, `organisations`, `custom_access_token_hook` — all `public`-schema objects on jvkn (eq-canonical) — are owned by **eq-cards'** migration ledger, not eq-shell's, even when the change is driven by an eq-shell function (`shell-join-tenant.ts`, `create-worker-invite.ts`) that reads/writes them. Confirmed by grepping both repos' migration history before writing new migration files.
- For auth-critical DB changes (the hook), applied directly via Supabase MCP `execute_sql` after verifying in a rolled-back transaction, then committed the matching migration file to the ledger afterward — same established pattern as migrations 0116/0117 earlier this week, not a new practice.
- Brief-gate flag naming bug hit again mid-session: the flag file must use the *current* date at write time, not a date copied from earlier in the conversation — the date rolled over from 2026-08-03 to 2026-08-04 partway through and a stale-dated flag silently failed to satisfy the gate.
