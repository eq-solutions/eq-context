# Session 2026-08-07 — My Schedule maps link: the real root cause was Shell's iframe sandbox, not iOS

## Built
- Third iteration on the maps-link bug (continuing from 2026-08-05/06). Royce reported the "fixed" v3.5.465 link still didn't work on his iPhone 16 — the icon visually highlighted on press (confirming the tap registered) but nothing opened.
- Asked one clarifying question before guessing again: how was Royce actually accessing Field? Answer: through Core (`core.eq.solutions/sks/field`), not a home-screen-installed standalone app. That single fact reframed the whole investigation — the two prior eq-field fixes (iOS-standalone `target` handling, `maps://` scheme) were real and correct for genuine standalone-PWA use, but neither could ever have applied to Royce's actual test, since `navigator.standalone` is false when accessing via a normal Shell session.
- Read eq-shell's `FieldIframe.tsx` directly and found the real cause: the iframe's `sandbox` attribute is `allow-same-origin allow-scripts allow-forms allow-downloads` — missing `allow-popups`. Without it, the browser silently blocks any `target="_blank"` link or `window.open()` call from inside the embedded app, with no error and no console warning. This explains every symptom cleanly: the hard no-op (v3.5.460's problem), the tap-doesn't-work-but-long-press-does (actually long-press wasn't really "working" either in this context — it likely never got confirmed, the earlier report was probably about the standalone case being tested separately), and now the `maps://` swap also silently failing.
- Checked `ServiceIframe.tsx` and `CardsIframe.tsx` — identical sandbox string, same origin commit (`30b92068`, 2026-08-01, which only ever documented the `allow-same-origin`/`allow-scripts` risk, never considered popups). This is a suite-wide gap, not Field-specific: any new-tab/app-handoff link in any of the three Shell-embedded apps has been silently broken through Core since that commit, on any device.
- Presented the finding and fix scope to Royce before touching eq-shell (cross-repo, its own deploy) — confirmed "fix all three."
- Built the fix in a fresh eq-shell worktree (`iframe-sandbox-allow-popups`): added `allow-popups allow-popups-to-escape-sandbox` to all three iframes' sandbox attribute. Verified locally: `pnpm run build:packages && build:tokens && tsc -b` clean, `vite build` succeeds, eslint shows 0 new errors (only pre-existing, unrelated findings in files this diff never touches).
- Hit a real, unrelated blocker opening the PR: GitHub Actions' `pull_request`/`push`-triggered CI wasn't firing at all for eq-shell — 0 workflow runs registered against the PR's commit, for any of the 4 required checks. Diagnosed methodically: confirmed scheduled/cron workflows were running fine all day (ruling out a repo-wide Actions outage or billing pause), confirmed `workflow_dispatch` could still run the CI job successfully (but a dispatch-triggered run doesn't attach to a PR's required-check evaluation the same way a `pull_request` event does), tried closing/reopening the PR (no effect) and pushing a fresh empty commit (no effect either) — all pointing to a genuine GitHub-side event-delivery issue specific to `pull_request`/`push` triggers on this repo, not anything wrong with the change itself or anything fixable from this environment.

He picked "wait and retry later." On the next status check, CI had recovered on its own — all 4 required checks (typecheck·test·lint, gitleaks, migration ledger hygiene, schema drift) plus the deploy preview passed clean.
