## Notes
- **Real gotcha, worth remembering for any future Sentry rule scripting:** Sentry's issue-alert filters split into `EventAttributeFilter` (a closed set of built-in attributes: message, platform, environment, etc.) and `TaggedEventFilter` (arbitrary tags, e.g. `transaction`, `role`, `tenant`). Both take a near-identical shape (`attribute`/`key` + `match` + `value`), which is exactly how I picked the wrong one the first time — I pattern-matched against the *other* rules in the same script (which correctly use `EventAttributeFilter` for `message`) instead of the *original* rule I was replicating (which used `TaggedEventFilter` for `transaction`, shown as "Tagged event" in Sentry's own UI/API description).
- The script's `deleteRule()` throws a client-side `"Unexpected end of JSON input"` on every single delete call (likely Sentry returns 200/202 with an empty body rather than a literal 204, and `res.status === 204 ? null : res.json()` then chokes on the empty body). This looks alarming in the log ("could not delete X") but the delete succeeds server-side regardless — confirmed by checking for duplicate rules after both runs (none, either time). Not fixed (cosmetic, script still works correctly end-to-end), but worth knowing so a future run's red-looking delete lines don't get mistaken for a real failure.
- **Lesson on trusting a "succeeded" CI run:** the workflow's own exit code was 0/success both times, including the first (buggy) run — GitHub Actions only sees that `node script.mjs` didn't throw an uncaught exception, not that every operation inside it actually worked. The script's own per-rule `✓`/`✗` console output was the only place the real per-rule failure was visible. Always read the actual log content for scripts that loop over multiple operations and swallow individual errors, not just the job's pass/fail badge.
