# Session 2026-08-04-g — Shared eq-context checkout: concurrent-session git races closed as F9, hook-enforced

## Built
- Royce reported the shared `C:\Projects\eq-context` checkout had hit its now-familiar concurrent-session collision pattern twice more in ~20 minutes: a read of `CLAUDE.md`/`system/worktree-registry.md` returning content mid-way through another session's active rebase (self-resolved), then a targeted `git add system/worktree-registry.md && git commit` sweeping up three files (`eq/pending.md`, `eq/changelog/eq-cards.md`, `sessions/2026-08-04.md`) another concurrent session had already staged — caught via `git show --stat HEAD` before push, undone with `git reset HEAD~1`, recommitted correctly scoped. The follow-up `git push` then hit a non-fast-forward rejection, `git rebase` refused to start (unrelated uncommitted files from another process already in the index), and `git stash` was blocked by an unrelated environment permission classifier — resolved via a fresh isolated clone + cherry-pick.
- Read `eq/pending.md`'s existing 2026-08-03 deferred item, `system/failures.md` (F1–F8), `system/lessons.md`, `.githooks/pre-commit`, `hooks/README.md`, `hooks/pre_tool_use.py`, `hooks/session_start.py`, `rules/agentic-coding.md`, and the 2026-07-14/2026-08-03 session logs to establish this failure class had **already recurred 3+ times (2026-07-14, 2026-08-03 ×3, 2026-08-04 ×2) with zero `system/failures.md` entry** — the exact gap the ratchet's own recurrence counter depends on not having.
- While reading (not writing), watched the shared checkout's `HEAD` advance from `63e4c3b` to `507e6a8d` between two consecutive read-only `git log` calls, with no command of mine touching it — a live demonstration of the problem mid-investigation. Moved all subsequent editing to an isolated clone in the scratchpad rather than continuing against the shared checkout, deliberately practicing the fix being built.
- Extended `hooks/pre_tool_use.py` with two new rung-4 checks (F9), both scoped to the ONE shared checkout by exact path (`is_shared_eq_context()`, `EQ_CONTEXT`-overridable, same convention `session_start.py` already uses) so the isolated-clone escape valve they recommend is never itself blocked, and deliberately **not** gated on `in_sandbox()` — every occurrence has happened natively on the Beelink:
  1. Blocks bare `git commit` (no `--` pathspec, no `--amend`) — a bare commit records the *entire* index, not just what was just `git add`ed, which is the exact mechanism that swept up a concurrent session's files today. Quoted message content is stripped before scanning for `--` so a commit message that happens to contain the literal text `-- ` can't create a false negative.
  2. Redirects `git rebase` / `git merge` / `git pull` to an isolated clone instead of the shared checkout — these mutate HEAD/index/refs across several non-atomic steps, the mechanism behind the stuck rebases, the conflict marker committed straight to `main`, and the detached-HEAD/stale-ref damage from 2026-07-14 and 2026-08-03. `--abort` / `--continue` / `--skip` stay allowed through unconditionally, so a session already stuck mid-operation can still get itself out rather than being trapped by the guard meant to prevent the stuck state in the first place.

## Decided
- Royce: "decide/implement a concrete fix — not just re-document the risk a third time," offering three candidates (fresh-clone-by-default, a lock/coordination file, mandatory `git status --short` before targeted add+commit) and asking for something enforceable, not prose.
- Chose a composite of (mechanical pathspec-commit rule) + (scoped fresh-clone redirect for rebase/merge/pull) over the three as literally framed:
  - **Bare-commit sweep (today's incident)** is fixed unconditionally by requiring `--` pathspec on every commit in the shared checkout — stronger than "check `git status` first" (candidate c) because it can't be forgotten, and doesn't depend on the operator noticing foreign staged content before committing.
  - **Ref-level corruption (2026-07-14, 2026-08-03)** is fixed by redirecting the specific multi-step, non-atomic verbs (rebase/merge/pull) to an isolated clone — narrower than "fresh-clone-by-default for every substrate write" (the full form of candidate a), which would have broken routine, currently-reliable automation (nightly cron commits, single-file pending.md ticks, session close) that has never been the source of the actual damage.
  - **Rejected outright:** a lock/coordination file (candidate b) — a hook-enforced lock needs reliable cleanup on abnormal session termination or it becomes a new stuck-forever failure class, and this ledger already documents several failures of exactly that shape (the Loop of Despair, F2, F6, F7 — all guards that had their own bugs). A lock also wouldn't have prevented today's incident: the foreign staged content came from a session that ended without committing, not from two sessions writing at literally the same instant.
- Not asked, so not done: did not touch `hooks/adversarial_test.sh`'s own F7/F9 gap (flagged as a deferred item instead) — reconciling or deprecating the legacy runner is a separate decision, not part of fixing the concurrent-write problem itself.
