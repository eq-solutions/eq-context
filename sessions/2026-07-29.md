# Session 2026-07-29 (cont.) — EQ Field: team pills as the single crew picker, plus a lazy-load race and a column-sizing bug

## Built
- Royce asked for a team selector on Edit Roster, "same as SKS NSW". Investigation found the pill UI already existed (`teams.js`, ported from SKS once before, v3.5.27) but was missing from Editor, and — everywhere it did render — never actually filtered anything (`personInActiveTeam()` was never called from any page's render function). A separate "My crew / a team / Everyone" dropdown was the only thing actually scoping fetches (Roster + Timesheets), also absent from Editor and Contacts.
- Consolidated onto the pill row as the single picker everywhere (eq-field [PR #563](https://github.com/eq-solutions/eq-field/pull/563), v3.5.375): wired `personInActiveTeam()` into Editor/Roster/Contacts/Timesheets' render functions; `getCrewPersonIds()` (permissions.js) now reads `STATE.teamFilters` instead of the retired `EQ_CREW_VIEW`; added three-state persistence (never-chosen / explicit-All / team ids) so a supervisor who's never touched the pills still defaults to their own crew, matching the old dropdown's default; removed the dropdown UI; rewrote `tests/crew-scoping.test.js`'s manual-widen section for the new mechanism (35/35 pass).

- Royce reported the pills still weren't showing on `core.eq.solutions/sks/field?tab=editor` after a hard refresh. Root-caused (not assumed): the deployed code was correct, but `renderTeamPills()` had a lazy-load race — only ever called before `teams.js`'s async lazy-load necessarily resolved, or (post-load) only for the `'teams'` page specifically. Same bug class this file has already fixed twice for `leave.js`. Invisible before because normal in-app navigation usually pre-loaded `teams.js` from an earlier tab; Core's cold `?tab=editor` deep link has nothing to paper over it. Fixed by calling `renderTeamPills()` from inside `renderCurrentPage()`, which only ever runs after the lazy-load resolves, for every page (eq-field [PR #565](https://github.com/eq-solutions/eq-field/pull/565), v3.5.377).

Widened to 108px, same PR.

# Session 2026-07-29 (cont.) — Maximo PDF import: job-plan matching + export bugs fixed, feature closed out end-to-end

## Built
- Fixed job-plan matching showing every real maintenance plan as "not found in EQ" during PDF import preview — the importer was matching on the E-number (e.g. `E1.25`) instead of the short plan code (e.g. `LVACB`); Maximo's raw text carries both, wrong one was being used as the DB key. Verified against all 5 real PDF files Royce provided. Deployed live via direct edge function deploy (v9); documented in eq-service [PR #630](https://github.com/eq-solutions/eq-service/pull/630).
- Fixed the Maintenance Plans page's CSV export only downloading the current page (26 rows) instead of the full filtered list (58 rows) — confirmed against a CSV Royce actually exported and compared to the live DB count. Added a second, unpaginated query for export only. eq-service [PR #630](https://github.com/eq-solutions/eq-service/pull/630), merged.
- Fixed a near-match suggestion bug Royce caught from a live screenshot: Maximo code `MVSWBD` was fuzzy-matching to `SWBD` instead of the obviously-intended `MVSWDB`. Root cause: the edit-distance check scored a 2-letter swap (`BD`→`DB`) the same as an unrelated bigger difference (dropping the `MV` prefix), so the tie fell to whichever plan the DB happened to return first — arbitrary, not the actual typo target. Switched to Damerau-Levenshtein so a swap counts as 1 edit, not 2 — the real target now wins outright. eq-service [PR #631](https://github.com/eq-solutions/eq-service/pull/631), merged.
- Merged eq-solves-intake [PR #79](https://github.com/eq-solutions/eq-solves-intake/pull/79) — catches up git history on everything already deployed live to the edge function across this whole thread (text-first extraction, both `WORKER_RESOURCE_LIMIT` fixes, the 5A frequency mapping, the job-plan-mnemonic fix).

## Notes
- `job_plans.code` is the short mnemonic (`LVACB`, `ATS`, `SWBD`); `job_plans.name` is the E-number (`E1.25`). This was the root cause of the job-plan-matching bug and is worth remembering for any future work on this importer.
